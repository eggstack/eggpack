## 1. Objective

Determine, using reproducible local/dry-run evidence, whether `dist` 0.33.0 can serve as a full, partial, or unsuitable backend beneath Eggpack for native application release production.

The spike must answer this before Eggpack commits to a large native build/packaging engine.

It is an evidence milestone only. It MUST NOT introduce `dist` as a production dependency, change a consumer repository, publish a release, or replace Eggup updater ownership.

## 2. Why this milestone is ready

This work has no hard dependency on Eggpack production code.

The external baseline is concrete and current: v0.33.0 exists as an immutable upstream release; its own release includes platform archives/checksums; it publishes `dist-manifest.json` and a schema; its release demonstrates installer generation; and its release exposes GitHub Artifact Attestations.

Eggstack already provides representative real-world requirements against which to test it.

## 3. Current implementation evidence

Eggstack producer-side patterns that the spike must model include:

- **eggsact/stegoeggo:** direct Rust binaries for Linux x86_64/AArch64, macOS x86_64/arm64, Windows x86_64, checksum sidecars, shell/PowerShell installers, and product smoke tests.
- **eggsearch:** direct binaries including ARMv7 and Windows ARM64, glibc 2.17 floor, QEMU/native qualification differences, and qualify-versus-release workflow mode.
- **Gregg:** sibling `gregg` + `greggd` binaries that form one logical release and must stay version-aligned.
- **CodeGG:** multi-runfile logical bundle.
- **Egress:** one archive containing `eggress` + `pproxy`, plus checksum sidecar.
- **Eggserve:** a richer producer policy model with native/deferred/QEMU qualification, musl/glibc distinctions, and a data-driven wheel matrix; this is reference evidence rather than required v1 native-backend parity.

The key question is not whether `dist` can ship a basic Rust binary. It is whether Eggpack can retain its own portable contract, qualification truthfulness, concrete manifest, and Eggup boundary while delegating enough generic machinery to justify the dependency.

## 4. Invariants that must not regress

- No production Eggpack dependency/backend decision is made inside the spike.
- Eggpack domain identity remains canonical; `dist` types/configuration are external adapter concerns.
- Eggup remains the updater/deployment mechanism for Eggstack self-update paths.
- The spike does not enable or adopt an external standalone updater.
- No public GitHub Release, crates.io package, PyPI package, Homebrew formula, or other public artifact is created.
- All external tooling is pinned to v0.33.0 for measured behavior.
- Unsupported requirements are recorded as unsupported; do not patch around them and then call them native support.
- Generated CI/installers are evaluated for reviewability and drift control, not merely successful generation.
- Qualification labels distinguish native, deferred-native, emulated/QEMU, and structural evidence accurately.
- Publication must remain independently gateable.

## 5. Scope

### In scope

Create an isolated research fixture area such as `research/dist-0.33/` containing only what is needed to reproduce the spike.

Evaluate:

1. simple direct binary release equivalent to eggsact/stegoeggo;
2. sibling multi-binary product equivalent to Gregg;
3. multi-runfile bundle shape equivalent to CodeGG where meaningfully different;
4. archive containing two required members equivalent to Egress;
5. Linux GNU x86_64/AArch64 with explicit compatibility floor requirements;
6. ARMv7 support/limitations relevant to eggsearch/SBC use;
7. Windows x86_64 and Windows ARM64 support/limitations;
8. macOS Intel/Apple Silicon;
9. build-host versus qualification-host representation;
10. QEMU/container qualification hooks;
11. product-specific bounded smoke hooks;
12. generated checked-in GitHub Actions shape;
13. shell/PowerShell installer generation;
14. checksum/final-artifact behavior;
15. `dist-manifest.json` semantics and stability;
16. feasibility of normalizing `dist` output into planned Eggpack ReleaseManifest fields;
17. GitHub Artifact Attestation integration;
18. ability to avoid/disable `dist` updater ownership;
19. draft/staging versus final publication controls;
20. operational/toolchain dependency cost.

### Explicitly out of scope

- committing `dist` to Eggpack Cargo dependencies;
- writing the production Eggpack backend;
- changing Eggpack canonical schemas;
- modifying any real consumer repository;
- publishing any release/package;
- benchmarking every competing release tool;
- evaluating end-user updater quality except to prove it can remain outside Eggpack/Eggup ownership;
- selecting authenticity/signing policy.

## 6. Required research artifacts

### Capability matrix

Produce `architecture/dist-0.33-evaluation.md` with a matrix covering each required scenario.

Each row should record requirement, supported-directly/supported-with-adapter/unsupported/unknown, exact evidence, generated artifact or command reference, and Eggpack integration consequence.

### Reproducible fixtures

Keep minimal fixture configuration/output snippets needed to reproduce claims.

Do not check in huge binary build products. Prefer text config, manifests, generated workflow/installer excerpts, and hashes of ephemeral outputs.

### Manifest normalization prototype

If `dist-manifest.json` contains enough information, write only a throwaway/research normalization script or mapping document answering how ProductId/ReleaseId/SourceRevision map, how target identity maps, how direct/bundle/archive artifact identity maps, whether exact final size/hash are available, how qualification/provenance references map, and which Eggpack-required fields are absent or ambiguous.

Do not turn this prototype into `eggpack-manifest`.

### Updater separation proof

Document exact configuration/command behavior showing whether generated installers/releases can be used without adopting a `dist` self-updater in the application runtime.

## 7. Ordered work packages

### Work package A — Freeze tool and inspect upstream contracts

Acquire/execute v0.33.0 through a reproducible method; record executable name/version output; inspect relevant configuration/schema/help for builds, installers, CI, manifests, attestations, and updater behavior.

### Work package B — Direct-binary fixture

Prove the common eggsact/stegoeggo case. Evaluate target matrix, checksums, installers, manifest, generated CI, product smoke hook, and publication separation.

### Work package C — Complex artifact forms

Test whether the backend naturally models Gregg sibling binaries, a CodeGG-like multi-runfile logical unit, and an Egress-like archive with declared members. Record whether `dist` preserves the logical relationship or merely emits unrelated artifacts requiring Eggpack-side aggregation.

### Work package D — Target and qualification edge cases

Evaluate glibc floor control, AArch64 native/cross behavior, ARMv7, Windows ARM64, native versus deferred qualification, and QEMU/container smoke. A target that builds but cannot be qualified according to policy must be recorded distinctly.

### Work package E — Manifest/CI/installer/provenance analysis

Inspect generated manifest/schema, GitHub workflow, shell/PowerShell installers, checksums, and attestation jobs/data. Assess whether checked-in deterministic generation and explicit publication gates can satisfy ADR-0003.

### Work package F — Normalization prototype and disposition

Map backend outputs to Eggpack's planned domain and choose one disposition.

## 8. Failure, cancellation, restart, and contention semantics

This spike must fail informationally rather than mutate production state.

If a scenario is unsupported, record the exact failure/limitation, preserve generated evidence, and continue independent scenarios where valid.

If exact v0.33.0 cannot be obtained/executed in the environment, mark affected evidence blocked. Do not infer runtime/generated-output support from documentation alone when empirical evidence was required.

No public release or registry state should need rollback because none may be mutated.

## 9. Compatibility and migration

There is no production compatibility commitment in M001.

Any fixture/config format checked in under the research area is disposable evidence and must be clearly labeled non-production.

If the disposition recommends adoption, a subsequent ADR must define supported backend version policy, delegated operations, normalization boundary, escape/fallback path, and upgrade compatibility/testing.

## 10. Required tests and evidence

At minimum record exact v0.33.0 version output; direct fixture plan/generate output; generated workflow/installer/manifest inspection; no-publication dry-run proof; target support matrix; complex artifact-form evidence; updater-separation evidence; attestation/provenance behavior; and normalization field matrix.

Where generated text/artifacts are deterministic, hash them so later upstream/tool changes are detectable.

## 11. Required verification commands

Because this is an external-tool spike, exact CLI spelling/options must be taken from v0.33.0 rather than guessed here.

The closure record must show exact commands used for:

- tool version output;
- plan/help or equivalent;
- generate/check or equivalent;
- fixture build/package dry runs;
- generated manifest inspection;
- generated CI inspection;
- generated installer inspection.

Also run `git diff --check`. If a research script is added, run its focused tests/static checks and record them.

Do not substitute documentation excerpts for commands when generated-output behavior is under evaluation.

## 12. Documentation updates

Required: `architecture/dist-0.33-evaluation.md`, external-backend roadmap status, planning registry, and closure record.

If the result recommends adoption/partial adoption, author the backend-selection ADR only after closure evidence is available.

## 13. Acceptance criteria

M001 closes when every in-scope Eggstack scenario has a supported/adapter/unsupported/unknown disposition; exact v0.33.0 runtime/generated-output evidence backs material claims; direct and complex artifact behavior are distinguished; target and qualification gaps are explicit; manifest normalization feasibility is documented field-by-field; generated CI/installers are assessed against Eggpack's reviewability/authority rules; updater ownership can remain outside Eggpack/Eggup or is identified as a blocker; publication can remain explicit or the limitation is identified; dependency/operational cost is documented; no public release/package was created; and one final disposition is recorded.

Disposition vocabulary:

- **A — primary backend candidate:** most native Eggpack producer mechanics can delegate to `dist`; follow with backend-selection ADR.
- **B — partial backend candidate:** specific bounded operations can delegate; follow with ADR defining the narrow boundary.
- **C — reference only / native Eggpack implementation preferred:** insufficient fit; record why and unblock native planning without adopting `dist`.
- **D — inconclusive:** named evidence/environment gap prevents a responsible decision.

## 14. Stop conditions

Stop and report rather than improvise if obtaining/testing exact v0.33.0 is impossible and the missing evidence is central; the spike would require publishing public artifacts; upstream configuration would require credentials unavailable for a non-publishing test; proving a feature would require modifying a real consumer repository; the research starts becoming a production backend implementation; or an external updater would need to replace Eggup to make the backend viable.

## 15. Closure evidence required

Record the Eggpack research SHA; exact `dist` version and upstream commit/tag; acquisition/verification method; per-scenario capability matrix; target/runner/qualification matrix; generated workflow/installer/manifest references or hashes; complex artifact-form findings; manifest normalization field matrix; updater-separation finding; publication-gate finding; attestation/provenance finding; operational/dependency cost; exact commands/results; unresolved findings/severity; final A/B/C/D disposition; whether a backend-selection ADR is required; and which downstream build/qualification planning is unblocked.

## 16. Handoff notes

Keep all spike artifacts clearly research-only.

Do not modify consumer repositories and do not add `dist` to Eggpack production dependency manifests.

The purpose is to prevent both forms of avoidable debt: reinventing a capable release backend without evidence, or wrapping an external system so heavily that Eggpack becomes more complex than a small native implementation.
