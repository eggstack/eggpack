# External Backend Evaluation Milestone 001 — dist 0.33 Capability and Interoperability Spike

Status: closed

Repository baseline: `cbe22eb3cbffc3ac5710837d0036bcba9290da02`

External baseline:

- upstream repository: `axodotdev/cargo-dist`
- evaluated release/tag: `v0.33.0`
- exact tag commit: `a1c829ffacb7ce98fb617b7acd7ffdd2282b45c2`
- release published: 2026-09-11
- observed release includes multi-platform archives, checksum sidecars, `dist-manifest.json`, `dist-manifest-schema.json`, installers/package metadata, and GitHub Artifact Attestations.

Primary class: infrastructure / architecture evidence

## 1. Objective

Determine, using reproducible experiments rather than feature-list assumptions, whether `dist` 0.33.0 should be:

A. used as an Eggpack backend for a meaningful subset of producer operations;
B. used only as an optional/simple-release backend;
C. used only as design prior art with selected output normalization;
D. rejected as a backend because wrapping it would add more complexity than native Eggpack machinery.

The spike MUST NOT make a production dependency decision itself.

## 2. Why this milestone is ready

- It is deliberately independent of Eggpack code bootstrap.
- The upstream version/tag is pinned.
- Current Eggstack repositories provide representative release shapes.
- Eggpack's ownership and publication invariants are already fixed by ADRs.
- A backend disposition is required before implementing a large build/qualification engine, avoiding premature reimplementation.

## 3. Current evidence

The reviewed `dist` v0.33.0 upstream release demonstrates:

- Rust application release packaging;
- Linux GNU/musl, macOS, Windows artifacts in its own release;
- checksum sidecars;
- machine-readable `dist-manifest.json` and schema;
- generated shell/PowerShell installation paths;
- Homebrew/npm metadata in its own release;
- GitHub Artifact Attestations;
- a release pipeline capable of creating publishable artifacts.

This is sufficient to justify a serious compatibility spike, not sufficient to establish Eggpack fit.

Eggstack-specific requirements requiring direct testing include:

- standalone direct binary releases;
- multiple sibling binaries as one logical release;
- one archive containing multiple required binaries;
- ARMv7/low-power SBC targets;
- Linux glibc compatibility floors such as 2.17;
- Windows ARM64;
- explicit native versus deferred-native versus QEMU qualification;
- product-owned smoke hooks;
- checked-in/reviewable CI;
- deterministic drift checks;
- manifest normalization;
- no external updater ownership replacing Eggup;
- human-gated final publication.

## 4. Invariants that must not regress

- No public release is created by this spike.
- No production Eggpack dependency on `dist` is added.
- Eggpack canonical target/artifact identity is not redefined around `dist` types.
- Eggup remains the intended consumer updater; `dist` updater features are disabled/ignored for architecture decisions.
- Unsupported capabilities are recorded as unsupported, not approximated into "works."
- A cross-built artifact is not credited with native qualification absent matching execution evidence.
- Generated CI must be inspected, not treated as opaque evidence.
- Publication capability must be separated from build/qualification capability.
- Exact tool version/commit and commands are recorded.
- Network credentials/tokens are not required for the core spike; use local/dry-run generation whenever possible.

## 5. Scope

### In scope

- install or build exact `dist` 0.33.0 in a controlled development environment;
- create small disposable fixtures representing real Eggstack release shapes;
- inspect generated plan/manifest/installers/workflows;
- test target/build/packaging configuration limits;
- examine how custom build/qualification hooks are represented;
- determine whether outputs can be normalized into future Eggpack ReleaseManifest without preserving backend-specific semantics;
- evaluate dependency/operational complexity;
- record a disposition matrix.

### Explicitly out of scope

- publishing a real Eggstack release;
- editing consumer repositories;
- adding `dist` as an Eggpack dependency;
- writing the final backend adapter;
- implementing Eggpack's own build engine;
- adopting `dist`'s updater;
- signing/authenticity design;
- broad comparison against every alternative release tool.

## 6. Required experiment scenarios

### Scenario A — Simple direct Rust CLI

Model an eggsact/stegoeggo-like product.

Required questions:

- can asset names be controlled to match Eggpack contract shapes?
- can Linux GNU x86_64/aarch64, macOS x86_64/aarch64, and Windows x86_64 be expressed?
- how are checksums and installers represented?
- is generated CI checked in and stable?
- what parts of target mapping become `dist` authority?

### Scenario B — Sibling logical bundle

Model Gregg-like `gregg` + `greggd` output and CodeGG-like multiple runfiles.

Required questions:

- can multiple executables for one product/target be kept as one logical release unit?
- can install names differ from release asset names?
- can failure of one member prevent aggregate success?
- does the manifest expose enough logical grouping to normalize safely?

### Scenario C — Multi-member archive

Model Egress-like `eggress` + `pproxy` archive.

Required questions:

- can one target archive contain explicitly required member mappings?
- can member source/install identity be expressed without custom opaque scripts?
- can archive contents be checked deterministically before publication?

### Scenario D — Target/compatibility edge cases

Probe:

- ARMv7 Linux GNU;
- AArch64 Linux GNU;
- Windows ARM64;
- Linux musl where useful;
- explicit glibc 2.17 or equivalent compatibility floor;
- macOS deployment floor controls.

Record "supported directly", "supported with hook/custom job", "not represented", or "unknown."

### Scenario E — Qualification truthfulness

Model:

- native smoke;
- cross-build plus later native smoke;
- QEMU/container smoke;
- structural-only artifact verification;
- product-owned bounded smoke command.

Determine whether `dist` can represent these as first-class release gates or whether Eggpack would have to generate/own additional CI around it.

### Scenario F — Manifest interoperability

Inspect `dist-manifest.json` and schema.

Map every field needed for proposed Eggpack ReleaseManifest:

- product/release identity;
- target identity;
- asset filenames;
- member/install identity;
- byte size;
- SHA-256;
- source revision;
- qualification status/evidence;
- provenance references.

Classify each as direct, derivable, missing, or semantically incompatible.

Do not decide to reuse the `dist` manifest format merely because it exists.

### Scenario G — Installer/updater boundary

Generate/inspect shell/PowerShell installers.

Determine:

- whether target mapping is data-derived;
- how integrity is checked;
- whether package-manager/source fallback is implicit;
- whether generated installers can operate without adopting the `dist` updater;
- whether updater installation can be disabled;
- whether Eggup can remain the sole normal self-update mechanism.

### Scenario H — CI/publication boundary

Inspect generated GitHub Actions.

Required questions:

- can final publication be human-gated/draft-only?
- are build and write permissions separable?
- can workflows be checked in and drift-tested?
- how pinned are actions/tool versions?
- can Eggpack wrap generation without hidden remote mutable policy?

### Scenario I — Provenance

Inspect GitHub Artifact Attestation integration.

Determine:

- what subject bytes are attested;
- source/workflow/commit identity available;
- whether attestations survive/compose with Eggpack's future manifest;
- whether use is optional;
- what runtime dependency, if any, would be imposed on consumers.

This scenario informs future work only; it does not select the authenticity policy.

## 7. Required production changes

This is an architecture spike. Production Eggpack code is optional and should be avoided unless a very small throwaway/prototype parser materially improves evidence.

Allowed repository additions:

- minimal fixture projects under an explicitly experimental/test path;
- small scripts that reproduce commands/normalization experiments;
- captured generated text/JSON samples when they are reasonably sized and license-compatible;
- documentation/evidence needed by closure.

Do not wire the spike into the future Eggpack public API.

## 8. Ordered work packages

### Work package A — Pin and inventory upstream behavior

Record exact binary/source version, installation method, relevant config schema, and commands.

### Work package B — Direct/bundle/archive fixtures

Construct the three logical release forms and capture what `dist` can/cannot model.

### Work package C — Target/qualification matrix

Exercise or statically prove platform/qualification representation. Distinguish build support from execution proof.

### Work package D — Manifest/installer/CI normalization analysis

Produce field/authority mapping tables and generated-output inspection.

### Work package E — Maintenance/security analysis

Record:

- dependency/tool installation footprint;
- custom scripts/actions required;
- action pinning behavior;
- update cadence;
- external updater implications;
- provenance support;
- likely adapter maintenance burden.

### Work package F — Disposition

Closure MUST choose one of A/B/C/D from Objective and justify it.

If A/B recommends production adoption, author a new proposed backend-selection ADR. Do not silently mark it accepted in the same spike unless maintainers explicitly approve after reviewing closure evidence.

## 9. Failure, restart, and contention semantics

Experiments should be rerunnable and side-effect-light.

Use local fixture directories and dry-run/generation modes where available.

No public publication, tag movement, registry upload, or production repository mutation.

If a command requires credentials merely to inspect generation behavior, document that as an operational requirement and use a non-publishing alternative rather than granting credentials for the spike.

## 10. Compatibility and migration

No compatibility commitment is created by this spike.

Any committed fixture/config using `dist` is experimental evidence, not a supported Eggpack format.

The eventual Eggpack architecture must be able to replace the backend without changing DistributionContract or ReleaseManifest semantics.

## 11. Required tests / evidence

For each scenario, record:

- exact command/config;
- pass/fail/not-supported;
- generated outputs inspected;
- key limitation;
- whether custom Eggpack glue would be required.

Required summary matrices:

1. feature/capability matrix;
2. target matrix;
3. qualification matrix;
4. manifest-field normalization matrix;
5. installer/updater ownership matrix;
6. CI/publication control matrix;
7. maintenance/dependency assessment.

## 12. Required verification commands

Commands are discovered during the spike because the exact `dist` CLI surface belongs to the pinned external version. The closure record MUST include exact commands actually executed.

At minimum also run repository hygiene after adding evidence:

```bash
git diff --check
```

If Rust fixture code is committed, format/check/test it with the toolchain required by the fixture and record that separately from Eggpack's eventual MSRV.

## 14. Acceptance criteria

M001 closes only when:

- exact `dist` 0.33.0 behavior was evaluated, not a floating newer version;
- direct, bundle, and archive needs were all addressed;
- ARM/SBC and Windows ARM64 questions were answered to the extent possible;
- qualification truthfulness limitations are explicit;
- manifest normalization feasibility is explicit;
- installer/updater separation from Eggup is explicit;
- generated CI/publication gating is inspected;
- provenance capability is characterized;
- maintenance/dependency burden is characterized;
- one A/B/C/D disposition is selected with evidence;
- no production dependency/release publication occurred.

## 15. Stop conditions

Stop and report rather than broadening scope if:

- the pinned release cannot be obtained/verified;
- meaningful behavior can only be tested by publishing a public release;
- the spike requires modifying real consumer repos;
- upstream behavior is ambiguous enough that source inspection is required beyond reasonable bounds—record the unknown and source evidence rather than inventing semantics;
- testing drifts into comparing unrelated package managers/build systems.

## 16. Closure evidence required

Record:

- exact upstream tag/commit and installation digest if available;
- environment/tool versions;
- all scenario configs/commands;
- generated artifact/manifest/workflow samples or bounded excerpts;
- seven required summary matrices;
- failure/unsupported cases;
- updater separation finding;
- proposed backend architecture if disposition A/B;
- reasons for rejection if C/D;
- unresolved unknowns with severity;
- next roadmap/ADR transition.

## 17. Handoff notes

The desired result is a decision, not a large prototype.

A good negative result is valuable: if Eggpack would need to wrap most of `dist`'s target, qualification, manifest, and publication model, disposition C or D may be the lower-maintenance architecture.

Conversely, if `dist` cleanly handles the generic build/archive/installer/CI work while Eggpack preserves canonical contracts/manifests above it, document that seam precisely so later implementation can avoid duplicating mature machinery.
