## 1. Objective

Correct the post-M002a/M003b/M003d generated-workflow execution findings before
any real GitHub draft qualification or consumer adoption.

No generated release workflow — exact or reusable — can currently execute to
completion. Every staging-capable render fails at one of seven deterministic
points: a `preflight` job that invokes the Eggpack tool it never installs, four
jobs that write into working directories they never create, an aggregate step
whose relative output root the finalization API rejects, and a qualify step
whose relative candidate directory forces every qualification into a failed
`InvalidRuntimeEnvironment` record without executing any smoke.

M003e must make the generated bytes executable end-to-end while preserving
every closed invariant: exact-source verification, one-writer staging, bounded
inputs, static drift detection, and the CLI/library path-safety contracts.

This corrective is a prerequisite for:

- resuming M003b live-draft qualification
- Ecosystem M001 adoption (its `eggpack_tool.revision` re-pin targets this
  corrective's implementation, not `398cd43`)
- Phase 8 completion
- any downstream consumer workflow that relies on generated release execution

No live draft should be attempted until M003e closes.

## 2. Post-closure findings

All seven findings were proven by driving the first real consumer
configuration (eggsact five-target shape: two CargoZigbuild Linux targets,
three NativeCargo targets, consumer validators, product wrappers,
`DispatchInput` staging) through the real `eggpack ci` entry points in a
disposable git repository, executing every generated command in order. The
scratch repository was removed afterwards; no consumer repository carries
uncommitted work from that review.

Severity is high for each finding: each one deterministically prevents a real
release run from completing. None of them weakens a security boundary; all of
them are execution-wiring gaps between individually correct components.

### Finding F1 — high: `preflight` invokes an uninstalled tool

The generated `preflight` job emits a `Verify checked-out release source`
step (`eggpack ci _verify-source ...`) but no `Install pinned Eggpack tool`
step, in both exact-staging and reusable renders.

In reusable mode the failure is doubled: the referenced release plan is the
runtime `eggpack-runtime/release-plan.json`, which the `resolve` job only
produces afterwards (`resolve` needs `preflight`).

Proven: the existing `m003b-*-staging.yml` goldens show the same shape, so the
defect predates M003d and affects exact mode too.

### Finding F2 — high: `resolve` never creates the runtime identity directory

The reusable `resolve` job writes three documents into `./eggpack-runtime/`,
but nothing creates that directory. `eggpack ci _resolve-release` fails with
`output parent is unavailable` because `atomic_write` deliberately requires a
real parent directory.

Proven by executing the exact generated `_resolve-release` argv in a fresh
checkout: fails before the fix, resolves distinct per-tag identity after
`mkdir -p ./eggpack-runtime`.

### Finding F3 — high: validate jobs never create their evidence directory

`validate_*` jobs write to `./eggpack-consumer/build_<job>/consumer-evidence.json`
without creating the parent. Same `atomic_write` failure as F2, in both modes
whenever validators are configured.

### Finding F4 — high: gate never creates its outcome directory

`required_gate` writes `./eggpack-gate/gate-outcome.json` without creating
`./eggpack-gate`. Same failure, both modes.

### Finding F5 — high: aggregate never creates its output directory

`aggregate` writes `./eggpack-finalized/summary.json` (plus the adjacent
`release-manifest.json`) without creating `./eggpack-finalized`. Same failure,
both modes.

### Finding F6 — high: aggregate output root is relative but must be absolute

The generated `_aggregate` step passes `--output-root ./eggpack-finalized/root`,
but `eggpack_core::finalize_release` requires an absolute root and rejects
anything else. The failure is deterministic in both modes.

The library requirement is deliberate (canonicalization, no traversal) and is
not relaxed by this corrective. The adapter layer (CLI) must bridge it.

### Finding F7 — high: qualify candidate directory is relative but must be absolute

The generated `_qualify-target` step passes a relative `--candidate-dir`
(`./eggpack-handoff/.../candidates`), but `inspect_candidate` requires an
absolute candidate path. Every qualification therefore records failed
`InvalidRuntimeEnvironment` with no executed process — the exact candidate is
never smoked.

This is the most dangerous finding in the set because it fails *quietly*: the
CLI still exits 0 after writing the failure evidence, so the defect would
surface only at the gate. Proven: relative dir yields
`Failed(InvalidRuntimeEnvironment)`; the identical invocation with an absolute
dir yields `Passed` with an executed `--version` smoke.

## 3. Corrective boundaries

Preserve:

- M001/M002/M002a build/qualification/finalization semantics
- M003a draft-only GitHub authority
- M003b one-writer permission model and static guards
- M003c exact-source verification and tag-source authority
- M003d reusable identity, product-wrapper presentation, consumer validators
- `atomic_write` refusal of symlink outputs and unavailable parents
- `finalize_release` absolute-root and no-traversal requirements
- `inspect_candidate` absolute-path requirement
- no publication endpoint, no tag mutation, no generic workflow DSL
- the finite action set (no new third-party action)

M003e may change generated job/step bytes (with golden regeneration),
`RunnerCommand` argv construction where a path must be created or absolutized,
and the two CLI entry points named in §6. It may not change library
validation semantics, evidence schemas, or any historical closure record.

## 4. Renderer fixes (exact and reusable)

All generated runtime working directories are renderer constants, so the
renderer creates them explicitly with auditable `mkdir -p` steps. No hidden
discovery is introduced: every created path is a fixed string already present
in the same job's CLI argv.

1. `resolve` (reusable only): a `Create runtime identity directory` step
   (`mkdir -p './eggpack-runtime'`) before `Resolve runtime release identity`.
2. `validate_<job>` (both modes, when validators are configured): a
   `Create consumer evidence directory` step
   (`mkdir -p './eggpack-consumer/<build_job_id>'`) before the validate step.
3. `required_gate` (both modes): a `Create gate outcome directory` step
   (`mkdir -p './eggpack-gate'`) before the gate step.
4. `aggregate` (both modes): a `Create finalized release directory` step
   (`mkdir -p './eggpack-finalized'`) before the aggregate step.
5. `preflight`: exact-staging renders install the pinned tool before
   `_verify-source`. Reusable renders drop `_verify-source` from `preflight`
   entirely: the runtime plan does not exist yet, `resolve` verifies HEAD
   during `_resolve-release`, and every later job re-verifies against the
   downloaded runtime identity. Exact non-staging renders are unchanged (no
   verify step exists there).

Build, qualify, prepare-stage, and stage jobs need no new steps:
`_capture-build`/`_qualify-target` create their `--output-dir`,
`_prepare-stage` creates its `--output-dir`, and the stage receipt and gate
payload parents are the workspace root.

`--output-root` keeps its portable relative form; the CLI bridges it (§6).

## 5. CLI fixes (adapter layer only)

6. `_qualify-target`: resolve `--candidate-dir` against the process working
   directory into an absolute path before reconstruction, mirroring the
   existing `absolute_path` treatment of the validated candidate in
   `_validate-consumer`. Relative inputs keep working; absolute inputs pass
   through unchanged; `..` components are rejected.
7. `_aggregate`: resolve a relative `--output-root` against the process
   working directory into an absolute path (via the canonicalized existing
   parent, which the generated workflow creates in §4 step 4) before calling
   `aggregate_finalize`. Absolute inputs pass through unchanged; `..`
   components are rejected. No evidence or manifest content changes: the root
   is a working directory, never serialized.

Both resolutions live in one small pure helper taking an explicit base so unit
tests never touch the process working directory.

## 6. In scope / out of scope

In scope:

- the five renderer changes in §4;
- the two CLI adapter changes in §5;
- renderer regression tests proving tool-before-use and mkdir-before-output
  for every generated job;
- CLI unit tests for the path helper plus renderer-derived argv coverage;
- regeneration of the seven affected goldens (`m002-*.yml` gate/aggregate
  mkdirs; `m003b-*-staging.yml` preflight tool install plus mkdirs);
- full local verification and a hosted CI run on the implementation SHA.

Out of scope:

- any relaxation of library validation (absolute-root, no-traversal,
  symlink refusal, evidence schemas);
- live draft execution (remains the M003b/Ecosystem M001 gate);
- consumer configuration (no eggsact change is claimed by this corrective);
- new actions, triggers, runners, or timeouts.

## 7. Failure and compatibility review

- A `mkdir -p` step can only fail on I/O errors; it creates no evidence and
  changes no authority.
- The preflight change removes a step that could never succeed (reusable) and
  repairs one that could never succeed (exact staging). No passing run is
  altered: any previously green exact-staging preflight would have required an
  ambient `eggpack` binary, which generated workflows must never assume.
- CLI absolutization only affects relative inputs; absolute inputs take the
  identical code path as before. `..` rejection is strictly narrower than
  current behavior (current behavior fails later with a less precise error).
- Golden regeneration is expected and recorded: goldens are test inputs, not
  historical closure records. No historical closure is rewritten.
- `ci check` on any previously generated workflow reports drift after this
  corrective, which is correct: previously generated bytes could not execute.

## 10. Acceptance criteria

M003e closes only when:

- F1–F7 are corrected per §4–§5 with no library semantic change;
- T1–T7 pass, including the two general render invariants;
- the seven goldens are regenerated and green;
- full local verification passes;
- hosted CI passes on the implementation SHA;
- the disposable end-to-end chain (resolve, build, capture, qualify,
  validate, gate, aggregate, prepare-stage) completes against the corrected
  tool with no manual mkdir/absolute-path workarounds;

## 11. Stop conditions
